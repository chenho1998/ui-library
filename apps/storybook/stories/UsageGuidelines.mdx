# Usage guidelines

Practical rules for choosing components, keeping pages accessible, and styling cleanly with `@yourorg/ui`.

## Choosing the right component

### Messaging: Banner vs Alert vs Toast

| Component | Scope | Persistence | When to use |
| --- | --- | --- | --- |
| `Banner` | Whole page or app shell | Stays until resolved or dismissed | Maintenance windows, plan limits, outage status, release announcements |
| `Alert` | One section or form | Stays while the condition holds | Inline validation summaries, payment warnings, section tips |
| `toast()` | Result of a user action | Auto-dismisses (except `toast.error`) | "Saved", "Copied", async status via `toast.promise()` |

Never put a critical, only-way-to-reach action inside a toast.

### Choosing from options: Select vs Combobox vs SegmentedControl vs RadioGroup

- **2–4 options that switch a view or mode**: `SegmentedControl` (always has one active value).
- **2–5 form options that benefit from descriptions**: `RadioGroup`.
- **5–15 static options**: `Select`.
- **15+ options, searchable lists, multi-select, or server-loaded options**: `Combobox`.

### Displaying tabular data: Table vs DataTable

- Use **`Table`** when you want full control over query state, external toolbars, or server-only sorting without extra UI chrome.
- Use **`DataTable`** when you want built-in search filtering, client-side (or `manualSort`) sorting, row selection with `bulkActions`, and `Pagination` out of the box.

### Overlays: Dialog vs AlertDialog vs Drawer vs Popover vs HoverCard

- **`Dialog`**: Focused modal task (forms, details). Closes on backdrop click and `Escape`.
- **`AlertDialog`**: Destructive or irreversible confirmation. Ignores backdrop clicks, focuses Cancel first, and stays open while an async `onConfirm` promise settles.
- **`Drawer`**: Edge-anchored panel for secondary workflows, filters, or mobile `Sidebar` navigation.
- **`Popover`**: Non-modal floating panel anchored to a trigger (pickers, quick filters).
- **`HoverCard`**: Sighted pointer preview only; never put unique actions inside it.

## Controlled vs uncontrolled state

Interactive components follow one consistent convention (powered by `useControllableState`):

- Pass **`defaultValue` / `defaultOpen` / `defaultPage` / `defaultIndex` / `defaultSizes`** for uncontrolled usage.
- Pass **`value` / `open` / `page` / `index` / `sizes`** together with its **`on*Change`** callback for controlled usage.
- Form controls (`TextField`, `Combobox`, `DatePicker`, `DateRangePicker`, `TimePicker`, `PinInput`, `FileUpload`, `ColorPicker`) accept `name` so they work directly with native HTML `<form>` submissions and `FormData`.

## Accessibility checklist

1. Always render `<ThemeProvider>` once at the root of your app (overlays portal inside it to inherit tokens and colour scheme).
2. Give icon-only buttons (`IconButton`), `SegmentedControl`, `ToggleGroup`, `TreeView`, `Carousel`, and `Resizable.Handle` an `aria-label`.
3. Every `Table` / `DataTable` requires a `caption` (hide it visually with `hideCaption` when a heading already introduces the table).
4. Keep heading levels sequential (`h1` → `h2` → `h3`); pass `size` on `Heading` or `level` on `Card.Title` / `Accordion.Item` to decouple visual size from semantic level.
5. Respect reduced motion: all library animations and `Carousel` auto-play automatically honour `prefers-reduced-motion: reduce`.

## CSS cascade layers and overrides

`@yourorg/ui/styles.css` lives inside `@layer ui.reset, ui.tokens, ui.components`. Any un-layered CSS in your app overrides component rules naturally without `!important`. Prefer overriding `--ui-*` tokens via `createTheme()` before writing selector overrides.

## SSR and React Server Components

- `@yourorg/ui` ships with `'use client';` at the top of its entry bundle for Next.js App Router compatibility.
- To prevent a flash of the wrong light/dark theme before hydration, place `getThemeScript('color-scheme')` inside an inline `<script>` in your document `<head>` and pass the same `storageKey` to `<ThemeProvider>`.
